Two-layer leaf module under `src/modules/customers/`:
- `services/` is the data layer. `types/customer-types.ts` defines a single Zod schema (`customerSchema`) plus the inferred `Customer` type; every other file imports from it. `customer-mock-data.ts` seeds demo records and centralizes dropdown enums (`services`, `statuses`, `priorities`). `customer-services.ts` exposes pure async functions (`getCustomers`, `createCustomer`, `updateCustomer`, `deleteCustomer`, `seedCustomersWithClient`, `getCustomerStats`) that call `@/lib/firebase/client` (`auth`, `db`) and enforce Row-Level Security by reading `auth.currentUser.uid` via `getCurrentUserId()` and attaching it as the `userId` field on every write.
- `components/` is the presentation layer. `data-table.tsx` is a generic `<DataTable<TData,TValue>>` built on `@tanstack/react-table` (core, pagination, sorting, filtering, faceting) composed of smaller sub-components (`data-table-toolbar`, `data-table-pagination`, `data-table-row-actions`, `data-table-view-options`, `data-table-column-header`). `add-customer-modal.tsx` is a client dialog form whose own Zod schema mirrors the base schema and calls an `onAddCustomer` callback supplied by the parent page.

Dependency direction: components → services (via callbacks / shared types); services → `@/lib/firebase/client`; no cross-imports between sibling component files beyond the shared `Customer` type. The module has no server entry point — it is consumed by pages that wire state and service calls together.
