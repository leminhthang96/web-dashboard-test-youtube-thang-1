Two-layer layout: `components/` holds TanStack Table-driven UI (data-table + toolbar + pagination + form dialog + role-assignment dialog) that is stateless and consumes plain `User` / `Role` / `UserRole` types; `services/` owns all persistence. Services split by entity — `user-services.ts` talks to `/api/admin/users` (Firebase Admin SDK on the server) for CRUD, falling back to in-memory `userMockData`; `role-services.ts` and `user-role-services.ts` hit Firestore directly via `getFirestoreCollection`, `setDoc`, `deleteDoc`, `writeBatch`. All runtime shape validation lives in `services/types/user-types.ts` using Zod schemas (`userProfileSchema`, `roleSchema`, `userRoleSchema`) plus separate form/payload schemas. Mock fixtures are JSON files under `services/data/` parsed at import time through their corresponding Zod arrays, so both real and mock paths return the same typed shapes. Seed helpers (`seedUsersWithClient`, `seedRolesWithClient`, `seedUserRolesWithClient`) batch-write fixtures into Firestore for local dev. Dependency direction is strictly components → services → types; services never import components.
